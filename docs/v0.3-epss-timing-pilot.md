# OT-RRDE v0.3 EPSS timing pilot

**Development experiment · 16 November 2026**

This pilot tests whether an EPSS value can influence a decision when the case dossier places the snapshot after the decision cutoff. It uses variants of the fictional `BENCH-014` case from the v0.2.1 benchmark and the first counterexample in the [research validation plan](v0.3-research-validation-plan.md).

## Case fields and decision rule

Select the experimental policy explicitly with `--policy policy/v0.3-dev.json`. The cutoff is the case's `recorded_at` timestamp. Both it and `epss_evidence.available_at` require an explicit UTC offset for the score to be eligible. The policy converts both timestamps to UTC and admits availability at or before the cutoff, including equality.

An optional `epss_evidence` object records the asserted snapshot. Its `snapshot_id` identifies the fictional source edition, `score_date` is the UTC calendar date assigned to the score, and `available_at` is the earliest instant the dossier asserts the snapshot was available to the decision-maker. The score date must be on or before the UTC availability date and the UTC decision date. The legacy `threat_data_as_of` field remains an aggregate data-quality signal.

```json
{
  "recorded_at": "2026-11-15T12:00:00Z",
  "epss_probability": 0.30,
  "epss_evidence": {
    "snapshot_id": "SYNTH-EPSS-2026-11-14",
    "score_date": "2026-11-14",
    "available_at": "2026-11-14T08:00:00Z"
  }
}
```

Missing or invalid snapshot metadata, inconsistent timestamps, and post-cutoff evidence make the EPSS value unavailable to both priority rules. Legacy cases can still run with the candidate and their other evidence can still drive triage. The case report retains the original probability in `input_signals` and records the snapshot, eligibility and exclusion reason in `epss_assessment`. The human-readable report includes the exclusion as a data warning. An asserted exploitation flag can trigger urgent human review while local reachability is unresolved.

## Observed results

Both policies received the same fictional input. The v0.2.1 policy reads the raw EPSS probability and the legacy aggregate date. The development policy also evaluates the per-score snapshot fields.

| Fictional input | v0.2.1 | v0.3 development policy |
| --- | --- | --- |
| High-severity case, EPSS 0.30 available before the cutoff | P1 | P1 |
| Same severity and score, snapshot dated one day after the decision | P1, with a date warning | P2, with the score withheld |
| Same case, score missing | P2 | P2 |
| Late EPSS snapshot, active exploitation asserted and reachability unresolved | Needs context review, with an urgent review flag | Needs context review, with an urgent review flag and an ineligible score |

A lower-severity synthetic case yielded P3 with a late score and P2 with an in-time score. Tests also cover same-day lateness, exact cutoff equality, offset conversion, missing metadata, inconsistent timestamps and an eligible score of zero.

Reproduce the matched results and check the published benchmark from the repository root.

```sh
python3 -m unittest discover -s tests -p 'test_epss_timing.py' -v
python3 -m unittest discover -s tests -v
python3 scripts/evaluate_benchmark.py
```

The Python 3.12 run passed 48 tests. The published v0.2.1 benchmark reproduced 15/15 policy-authored regression labels. The pilot checks timestamp consistency for supplied synthetic assertions. Evaluating the correct daily edition, snapshot authenticity, freshness, KEV or report provenance, and decision quality requires the later experiments in the validation plan.
