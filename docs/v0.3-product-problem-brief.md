# OT-RRDE: practitioner feedback brief

**23 November 2026 · Independent research by Yassar Sambo · v0.3 development**

**I am seeking feedback from OT vulnerability analysts, operations engineers and asset owners.** Would the workflow below address a problem you encounter? A short written response or a 10–15 minute conversation would help, including if your current approach already works well.

## Problem to explore

An OT vulnerability review may bring together vendor advisories, asset records, threat information and change prerequisites. I am investigating whether reconciling missing, conflicting or differently dated records creates significant effort or weakens the justification for the next step. The frequency and importance of this problem remain unvalidated.

## What exists and what is proposed

- **Built:** v0.2.1 is a published offline Python prototype that applies explicit rules to structured, fictional case records. It separates human investigation urgency from candidate remediation actions and lists missing prerequisites. Development code checks supplied EPSS exploitation-probability score timestamps; it does not authenticate the source.
- **Proposed:** a workflow that imports permitted offline records and produces a decision note showing what was known at a specified review time, where each claim came from, unresolved disagreements and evidence still needed. General conflict and correction handling remains to be built. Qualified humans retain change authority.

**Fictional illustration:** an asset register lists gateway software build 4.2, while a maintenance entry lists 4.3. A vendor advisory covers 4.2, and an inventory update arrives after the review date. How would your process handle these records? This illustration is separate from the formal pilot cases.

## Questions for practitioners

1. How do you currently prepare and approve a vulnerability decision? What works well?
2. Where, if anywhere, do evidence gaps or disagreements create extra work? A non-confidential example and approximate effort would help.
3. Would the proposed note add value to your existing process? What would make it unnecessary, difficult to use or worth testing?

## Existing work and participation

[SSVC](https://certcc.github.io/SSVC/howto/deployer_tree/) already considers mission, safety and exposure. [Tenable](https://docs.tenable.com/OT-security/Content/operational-playbooks/prioritize-mitigate-vulnerabilities.htm) and [Claroty](https://claroty.com/platform/exposure-management/) document contextual prioritisation capabilities. Whether this proposal adds anything useful remains an open question. Synthetic checks have not established operational effectiveness or commercial demand.

Personal views and general examples are sufficient; please omit confidential information. I will ask permission before naming or quoting contributors.

**Interested in independently scoring cases?** Request a standalone case packet before viewing project results, and disclose project material you have already seen. This public repository contains outputs elsewhere, so visiting it cannot guarantee a blinded review.
