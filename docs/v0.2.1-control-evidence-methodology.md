# OT-RRDE v0.2.1 — Control-evidence and challenge-benchmark methodology

**Date:** 15 November 2026. **Status:** uncalibrated, synthetic-only research policy. This extension is deliberately separate from v0.1 and v0.2.

## Research question

What information is needed before an OT risk tool can treat a compensating-control *claim* as a plausible, attack-path-relevant protective measure without confusing the presence of an asserted control with real-world effectiveness?

## Evidence rules

The optional fields on each fictional `compensating_controls[]` entry are:

- `control_type`: `network_isolation`, `access_control`, `monitoring`, `other`
- `attack_path_relevance`: `relevant`, `irrelevant`, `unknown`
- `verification_as_of`: ISO 8601 date of the alleged test/evidence

For v0.2.1, an entry is *credited as a consistent synthetic evidence assertion* only when `effectiveness=verified`, the declared relevance is `relevant`, a recognised type is supplied, and the date is not in the future or older than **90 days** relative to the case date. This 90-day threshold is a **research heuristic**, not a standard, vendor requirement or calibrated security assurance period.

For an input marked `reachability=isolated_verified`, a synthetic evidence record must include a credited, relevant `network_isolation` entry. Otherwise the triage changes to `NEEDS_CONTEXT_REVIEW` (unless the case is already unresolved because applicability is unknown) and the candidate action becomes `GATHER_EVIDENCE_AND_ESCALATE`. The original case's `reachability_verified` assertion alone is insufficient under this research rule.

No control reduces exploitation indicators or investigation priority. A credited control remains only an **internally consistent statement supplied in fictional data**, not independently authenticated effectiveness. Proper evaluation would require attack-path scope, timing, topology, evidence provenance, and expert assessment.

## Benchmark design

[`data/challenge_cases_v0.2.1.json`](../data/challenge_cases_v0.2.1.json) has **15 fictional cases**, constructed by modifying five existing fixture templates. It includes critical availability/redundancy constraints, unknown applicability, stale evidence, claimed isolation and a control irrelevant to the attack path. These scenarios are intentionally synthetic, not statistically independent, and cannot support external accuracy claims.

Each case contains an expected research-policy outcome. These labels are **authored from the policy itself**, not obtained from independent OT practitioners. Reporting “15/15 matched” would mean *regression consistency*, not a validated decision accuracy rate.

Use:

```powershell
py main.py --input data/challenge_cases_v0.2.1.json --policy policy/v0.2.1.json --output reports/v0.2.1_results.json --report reports/v0.2.1_comparison.md
py -m unittest discover -s tests -v
py scripts/evaluate_benchmark.py
```

The benchmark analyzer produces `reports/v0.2.1_benchmark.md` with descriptive counts and a baseline ranking. It performs no external network access.

## Concrete falsification targets

1. Can contradictory or genuinely ineffective firewall evidence still be credited by the simplistic fields?
2. Does a blanket 90-day limit misclassify stable network-isolation proof or fast-changing endpoint safeguards?
3. Can a synthetically credited control conceal a vulnerability exploitable via another path or source?
4. Does treating unknown isolation as unresolved create an unacceptable human-review workload?
5. How should safety, process dependencies and asset criticality inform mitigation feasibility instead of numerical priority alone?

## What has **not** been established

No independent recognition, product-market fit, measurable security benefit, safe operational change, expert approval, live OT deployment or novelty relative to vendors/SSVC workflows has been demonstrated. The repository remains a research prototype.

**Reviewers should challenge the classification semantics and test design rather than be asked to validate a predetermined endorsement claim.**
