# How I plan to test the idea

*Yassar Sambo, 23 November 2026*

Could another engineer looking back at a vulnerability decision tell what the team knew at the time? I want to know how teams do this today and whether a short note would make the job easier. [Practitioner feedback brief](v0.3-product-problem-brief.md).

Some links below show the software’s results. If you’d like to rate cases independently, ask me for the case sheets before opening those links.

## What the software can do

The published prototype (v0.2.1) reads fictional cases in a set format. It suggests when to investigate, explains why and lists checks needed before a change. The people responsible for the equipment decide whether to act.

The version in development checks the dates supplied for a score from the Exploit Prediction Scoring System (EPSS). The score estimates how likely attackers are to use a vulnerability. A missing, inconsistent or late date can rule out the score. The code trusts the source details entered in the case. Verifying the source and checking that the correct daily score was supplied are further work. [Timing check and examples](v0.3-epss-timing-pilot.md).

The proposed note would cover one asset, one vulnerability and one decision. It would use records the team is allowed to share offline and show what each source said, when the information arrived, where the sources disagreed and what still needed checking. Importing such records and tracking later corrections are still proposed features.

## Ask how teams work today

I plan to speak with three to five people across at least two organisations, including analysts who prepare reviews and the operations engineers or asset owners who act on them. A security lead might sponsor a trial. I’ll ask the people doing the work to walk me through a recent review. What worked well? Who approved the next step? How often do they do this, how long does it take, and does anything have to be done twice?

CERT/CC’s Stakeholder-Specific Vulnerability Categorization (SSVC) already considers safety, exposure and the impact on operations. Tenable and Claroty also describe ways to prioritise work on affected equipment. The interviews should establish whether people already have what they need. [SSVC decision guide](https://certcc.github.io/SSVC/howto/deployer_tree/) · [Tenable’s guidance](https://docs.tenable.com/OT-security/Content/operational-playbooks/prioritize-mitigate-vulnerabilities.htm) · [Claroty’s description](https://claroty.com/platform/exposure-management/).

## Compare the decisions

Two independent reviewers would each assess 24 new fictional cases in 12 related pairs. I’ll reserve all 12 pairs for this test. Before scoring, I’ll record the exact cases, software and rule versions, how cases are entered into each tool, and how answers will be assessed. [Study plan](v0.3-research-validation-plan.md).

How soon should someone investigate? How soon should a fix be deployed, if it applies and the team is ready? Reviewers will answer these separately. All eight pilot cases lacked at least one fact needed to calculate a priority using SSVC. Only one case met the study’s conditions for rating a proposed patch, and final change approval was still pending. I’ll keep the original case sheets and save any added facts in a dated revision. [Eight-case comparison with software results](v0.3-ssvc-pilot-mapping.md) · [Original case sheets and blank form](v0.3-reviewer-pilot.md).

I’ll check whether the new rules meet four aims on these cases.

- No suggestion to go ahead with a patch overlooks a stated reason to hold it or skips a required safety review.
- Later information has no effect on the earlier decision in the timing tests.
- Fewer decisions rely on unsupported evidence than with v0.2.1.
- Cases both reviewers judge urgent still get escalated whenever v0.2.1 escalates them.

For each check, I’ll report how many cases qualified and how many met it. I’ll count missed urgent cases, routine cases escalated, unresolved cases and which actions both reviewers accepted. I’ll keep disagreements visible and mark a finding inconclusive if too few cases can be judged. Results apply to the fictional cases tested.

## Collect independent reviews

Each reviewer gets the case sheets, instructions and a blank form. The packet leaves out the software’s answers, expected ratings and the list of paired cases. I’ll record the file version and checksum so the copy can be verified later. I’ll also record when I sent it, what else the person saw and when they finished scoring. The public repository and comparison workbook both contain results. If a reviewer has seen any, I’ll record which cases that affects. They can still comment on the study design. I’ll agree how to use each person’s feedback and ask separately before quoting or naming them.

## Decide whether to build more

I’ll propose an offline trial if practitioners independently describe the same unresolved problem and a team agrees what improvement would justify the effort. We’d try the current process and the proposed note, varying which goes first. We’d measure time spent entering and reviewing records, questions sent back, and which suggested actions the reviewers accept. We’d agree the time and quality targets beforehand.

If current tools already solve the problem, or writing the note adds more work than it saves, I’ll reconsider it. Who would pay, what it would take to adopt the tool and what it would be worth are still open questions.
