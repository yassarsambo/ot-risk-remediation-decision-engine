## What changed

The brief now opens with a fictional example. An equipment register and a maintenance note give different versions of the same software, and a correction arrives after the review. Readers can describe how they handle this today, including what already works and whether another note would add work. [Revised brief](v0.3-product-problem-brief.md).

The wording distinguishes the published prototype, v0.2.1, from the work on v0.3. The development code checks the dates supplied for one forecast. The proposed note would also show disagreements and later corrections. That part still needs to be built.

The study plan and the pilot results belong with the detailed research notes. The brief tells volunteers how to request the case sheets before seeing the software’s answers. If a reviewer has already seen results, that needs to be recorded with their feedback. [How the study would work](v0.3-product-validation-notes.md).

## What the evidence supports

All eight pilot cases lacked information needed to calculate a priority with CERT/CC’s method for deciding when to deploy a fix. That explains the “0 of 8” figure. How quickly a person should investigate is a separate question.

The three sources checked on 23 November show that existing methods and tools already consider the equipment and the possible effect on operations. Whether this project helps people make a better decision or saves them time still needs independent testing. Even if every fictional test case passes, safe use on working equipment would need separate evidence.

The next evidence to collect is a recent example from a practitioner and, separately, independent ratings of cases with enough detail to compare the methods fairly.
